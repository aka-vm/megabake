# Borrow Hazy's warp roles, skip its VM

The most useful thing megabake can take from HazyResearch is the runtime structure underneath their interpreter, not the interpreter itself. Every megakernel they built pairs three things. Warp roles (loader, consumer, storer, controller) persist across instructions. Shared memory is cut into pages that pass from one instruction to the next in a known order. Cross-SM dependencies are tracked with counters at a finer grain than whole ops. Together these let the next op's weights start loading while the current op is still draining. That is the capability megabake measurably lacks: its GEMM pipelines fill and drain inside every phase, its weight-streaming experiment stalled because warp 0 blocks on the TMA queue while also taking part in CTA syncs, and its decode time is set by fixed per-phase latency rather than by barriers. Hazy's later history also backs megabake's compiler-first bet. The hand-written VM, with its hard-coded barrier counts and hand-written page-release tables, was deleted from ThunderKittens main in January 2026. The 2026 MegaKittens rewrite (mk-v2) moved toward exactly what megabake already is: trace a graph, cut it into tiles, derive barriers automatically, and generate the dispatch code. Megabake should therefore keep its IR, its static schedule and its grid barriers as the default, and change three things in this order: give the megakernel fixed warp roles with a dedicated producer warp, add a compiler-owned page pool for shared memory, and add counters only on edges where that producer warp can use them. It should not copy the generic opcode interpreter, the per-op hand tuning, or the agent-written bespoke kernels that Hazy's "Retire the Abstractions" post endorses.

Two caveats on sources. **The Flapping Airplanes thread has no architecture content.** Its six tweets announce a $1B Series A and claim "the world's most complete megakernel framework", with no instruction format, scheduler or numbers ([FA tweet 2](https://x.com/flappyairplanes/status/2112955825367269788)). **"Kittens VM" is an inference.** The thread never uses the phrase. The only artifact matching it is the Megakernels interpreter, whose per-SM state object is named `kvms` and which its authors call "the VM" ([controller.cuh](https://github.com/HazyResearch/Megakernels/blob/main/include/controller/controller.cuh)). This report treats that interpreter (ThunderKittens `prototype/vm`, later the Megakernels repo) as the Kittens VM.

## Hazy abandoned the VM but kept its ideas

Hazy's megakernel work went through four stages in about sixteen months, and each stage tells megabake something different. The May 2025 low-latency Llama-1B VM ran static per-SM instruction queues and reached **78% of H100 memory bandwidth, about 2.5x vLLM** ([No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)). The September 2025 throughput VM added a global atomic work queue and in-kernel communication, and the authors called the code "sensitive to compiler versions, GPU setup, and sometimes even being looked at the wrong way" ([TP-Llama main](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-main)). On 2026-01-11 the TK 2.0 commit **deleted `prototype/vm`, `demos/kvm-runner` and `tests/vm` from ThunderKittens main**, in a commit that removed 53,639 lines ([commit e463ed89](https://github.com/HazyResearch/ThunderKittens/commit/e463ed89)). Development then moved to the Megakernels repo's `mk-v2` branches, "MegaKittens", a Blackwell-only runtime that "fuses PyTorch operator graphs into a single persistent CUDA kernel". Its last commit is from May 2026, and the repo contains no performance comparison against the original VM ([mk-v2 README](https://github.com/HazyResearch/Megakernels/blob/mk-v2/README.md)). Finally, in August 2026, Sul and Ré wrote that they built Cursor's MoE megakernel "but we deleted the abstraction", and that the framework's role as "cognitive offloader" now belongs to coding agents ([Retire the Abstractions](https://hazyresearch.stanford.edu/blog/2026-08-05-retire-the-abstractions)).

What they say got deleted is the scaffolding, not the ideas. MoK still overlaps "instructions ... at the SM task level", still signals between SMs "through a local counter", and still uses a device-side schedule table ([Cursor MoK](https://cursor.com/blog/mixture-of-kittens)). The blog closes with "Abstractions retire. Ideas stay." Its strongest caveat applies directly to megabake: **"We can only retire a layer once we have an oracle that outlives it"**. They list that oracle as reference implementations, numerics tolerances and "our intuition of what the profiled Gantt chart should look like" ([Retire the Abstractions](https://hazyresearch.stanford.edu/blog/2026-08-05-retire-the-abstractions)). The blog also gives an argument for keeping a compiler like megabake. A shared abstraction is where "application, reuse, and review attach", while "ten teams generating bespoke megakernels have ten disjoint sets of problems." The hardest problems Hazy names are "designing these custom instruction sets, and coordinating (and especially debugging) synchronization patterns" ([TP-Llama main](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-main)), and both are things a graph compiler derives automatically.

| Hazy artifact | Date | Status | What megabake should take |
|---|---|---|---|
| TK `prototype/vm` / Megakernels `main` | 2025-04 to 2025-06 | Deleted from TK main (2026-01); Megakernels main frozen | Role warps, page hand-off, counters, timing slots |
| Megakernels `throughput` branch | 2025-09 | "research reference, as opposed to a product" | Evidence that dynamic queues pay only for ~100 µs instructions |

| Cursor MoK | 2026-08 | Bespoke, agent-built | Software SM partitioning, the oracle discipline |

## Kernel bodies: persistent roles beat per-phase pipelines

### What Hazy built

In the VM, an op is a C++ struct with a static `opcode` and five nested role structs: `controller`, `loader`, `launcher`, `consumer` and `storer`. Each warp role runs its own loop over the instruction stream ([util.cuh MAKE_WORKER](https://github.com/HazyResearch/Megakernels/blob/main/include/util.cuh#L260-L304)). The roles are fixed for the whole kernel. **Warps 0–15 are consumers raised to 104 registers. The last warpgroup is lowered to 64 registers and holds the loader, storer, launcher and controller** ([megakernel.cuh](https://github.com/HazyResearch/Megakernels/blob/main/include/megakernel.cuh#L118-L140); [config.cuh](https://github.com/HazyResearch/Megakernels/blob/main/include/config.cuh#L24-L51)). Because a warp's role never changes, `setmaxnreg` can be applied once at kernel start. Ops reuse shared pipelines through hooks: `matvec_pipeline<..., pipeline_specifics>` calls `pipeline_specifics::load_iter`, `::store` and `::gmem_wait`, and `rms_matvec_pipeline` adds an RMSNorm prologue ([matvec_pipeline.cuh](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/matvec_pipeline.cuh#L5-L12)). In the matvec ops, loader lane 0 issues weight TMA loads, consumers compute partial results, and the storer reduces them, runs the epilogue, issues a TMA store and bumps the global counter ([matvec_pipeline.cuh](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/matvec_pipeline.cuh#L117-L243)). Residual adds go through a TMA reduce-add store, so no separate reduction op is needed ([matvec_adds.cu](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/matvec_adds.cu#L75-L80)).

Shared memory is **13 pages of 16 KiB**. The page order for instruction N+1 is computed from the previous op's `release_lid` permutation, so "the interpreter automatically passes released pages to the next instruction, allowing them to start issuing memory loads as early as shared memory becomes available" ([No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles); [controller.cuh](https://github.com/HazyResearch/Megakernels/blob/main/include/controller/controller.cuh#L74-L99)). The profiled transition in the throughput post shows the payoff: the next instruction "issues loads for first 2.5 stages, before stalling due to lack of available shared memory pages". Their pipelining ablation cut the inter-instruction gap from **10.2 µs to 3.4 µs, worth more than 7% on those instructions** ([TP-Llama main](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-main)). mk-v2 keeps the design with fewer, larger pages: 8 consumer warps at 224 registers, 4 other warps at 56, and `PAGE_SIZE = 32768` as "the only knob and everything else is derived" ([mk-v2 schema.cuh](https://github.com/HazyResearch/Megakernels/blob/mk-v2/csrc/schema.cuh#L46-L74)).

Three of Hazy's own outcomes argue against copying the design wholesale. First, the VM's **104-register consumer budget, against 224–232 in standalone TK GEMMs**, is the cost of fitting the union of every op's consumer code into one kernel ([TK OLD config.cuh](https://github.com/HazyResearch/ThunderKittens/blob/50ee1f0a/prototype/vm/config.cuh#L50-L51); [TK README GEMM](https://github.com/HazyResearch/ThunderKittens/blob/67845f5f/README.md#L107-L122)). Second, `release_lid` is a hand-written 13-entry permutation per op, with branches on `iters % 3` and the comment "NOTE: assumes a three stage pipeline" ([matvec_pipeline.cuh](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/matvec_pipeline.cuh#L70-L102)). mk-v2 still asserts `NUM_PAGES == 7 && LOAD_PIPE_DEPTH == 4` inside the GEMM's release order ([mk-v2 gemm.cuh](https://github.com/HazyResearch/Megakernels/blob/mk-v2/csrc/itypes/gemm.cuh#L37-L45)). Third, TK 2.0's flagship Blackwell GEMMs no longer use the LCF/LCSF callback templates. They hand-write `if (warpgroup::groupid()==...)` role branches over raw primitives ([bf16_b200_gemm.cu](https://github.com/HazyResearch/ThunderKittens/blob/67845f5f/kernels/gemm/bf16_b200/bf16_b200_gemm.cu#L117-L252)), and one NVFP4 kernel dropped register reallocation entirely ([commit 261018c6](https://github.com/HazyResearch/ThunderKittens/commit/261018c6)). Hazy's own attention body also wastes **75% of its MMA** on 16-row tiles with "only 4 rows are used" ([attention_partial.cu](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/attention_partial.cu#L6-L37)).

### What megabake does today

In the table megakernel, every body runs on the same 256 threads. **Only the forked CUTLASS GEMM is warp-specialized**, with one TMA producer warpgroup and one WGMMA/epilogue warpgroup ([cutlass_gemm.py:245-266](../src/megabake/bodies/cutlass_gemm.py)). Generic and attention bodies use every thread uniformly and call `sync_threads` ([generic.py:226-245](../src/megabake/bodies/generic.py)). Register reallocation exists (`load_register_requirement = 40`, `mma_register_requirement = 232`) but is disabled because "mixed megakernels run other bodies on the same warps afterwards" ([cutlass_gemm.py:268-275](../src/megabake/bodies/cutlass_gemm.py)). Each GEMM phase creates, fills and drains its own pipeline. On SmolLM-135M decode, the remaining time sits in **four small GEMM intervals per layer at ~3–4 µs each, "mostly pipeline fill"**, plus attention at ~6 µs on 9 CTAs ([ROADMAP.md:35](../ROADMAP.md)).

Weight streaming shows where this structure runs out. The barrier was split into arrive and wait halves, and warp 0 issued `preload_table` TMA loads between them ([codegen.py:1911-1941](../src/megabake/codegen.py); [cutlass_gemm.py:718-820](../src/megabake/bodies/cutlass_gemm.py)). Against the inert-code control, the preloads alone moved decode by **−0.5% (135M), −0.7% (1.7B), +0.9% (Qwen2) and +1.5% (DeepSeek)**. Issuing 13 stages took a median of ~1,000 and a p90 of ~4,000 cycles, because warp 0 blocks once the TMA queue is full. The recorded diagnosis is that streaming "needs a producer warp decoupled from the CTA's syncs" ([weight-streaming-step3](/home/dev/.claude/projects/-workspace-megabake/memory/weight-streaming-step3.md); [ROADMAP.md:47-65](../ROADMAP.md)). The workaround also needed a tag hidden in the GEMM's shared storage (`STREAM_TAG_SLOT`) and a context manager that suppresses mbarrier init (`_without_mbarrier_init`) ([cutlass_gemm.py:124-128](../src/megabake/bodies/cutlass_gemm.py)).

The register-allocation problem has the same root cause. A GEMM-only change moved untouched attention from 4.95 to 5.65 µs per phase when registers dropped from 244 to 128. The shape-agnostic table GEMM cost 2–4% for the same reason and was reverted ([ROADMAP.md:45](../ROADMAP.md); [cute-dsl-kernel-gotchas](/home/dev/.claude/projects/-workspace-megabake/memory/cute-dsl-kernel-gotchas.md)).

### The lesson

Megabake's per-phase pipelines and Hazy's roles differ in one decisive way. **Hazy's loader is a warp that never joins consumer synchronization and never stops existing between ops.** Weights are read-only, so a persistent loader can fetch the next op's weights with no dependency wait, limited only by free shared memory. Megabake has to hand that work to a warp that must later rejoin a `sync_threads`, so the TMA queue's back-pressure lands on the critical path. Fixed roles also make per-role register budgets legal again, which turns register allocation from a whole-kernel accident into a declared contract. The register-budget numbers (104 in the VM versus 224 in mk-v2) say to keep the consumer group small and fat: two consumer warpgroups at high register counts, not sixteen thin warps.

### Recommendations, in priority order

**K1 (highest): adopt a fixed role layout for the table launch.** Use one producer warp that owns all TMA traffic (GEMM A/B stages, weight preloads, and optionally activation tiles) and two consumer warpgroups. Convert generic and attention bodies to consumer-only code that synchronizes with named barriers (`bar.sync id, 256`) instead of `sync_threads`. ROADMAP already reaches this conclusion ("generic and attention bodies on 7 warps, with named barriers", [ROADMAP.md:65](../ROADMAP.md)). The Hazy evidence says it is the precondition for streaming, not an optional extra. Once roles are fixed, re-enable `setmaxregister` per role at kernel entry and record each role's budget in `ParticipantContract`.

**K2: keep GEMM pipeline state alive across phases.** Keep the producer/consumer ring index and phase bits in registers for the whole kernel. TK packs arrived and finished parity into one `uint32` initialized to `0xFFFF0000` ([TK util.cuh](https://github.com/HazyResearch/ThunderKittens/blob/67845f5f/include/common/util.cuh#L431-L453)). The producer can then fill stages for GEMM N+1 as soon as GEMM N's consumers release them, and the per-phase mbarrier init that `_without_mbarrier_init` works around goes away. This is the change aimed at the "mostly pipeline fill" intervals.

**K3: write bodies as role functions with hook slots.** A body should export `load(stage)`, `compute(stage)` and `store()` pieces plus prologue and epilogue hooks, mirroring `matvec_pipeline` + `pipeline_specifics`, rather than a monolithic `run`. This is ARCHITECTURE §9's "mega bodies with typed prologue/epilogue hook slots" ([ARCHITECTURE.md:133-152](../ARCHITECTURE.md)). Hazy shows it is the right granularity for a role-split runtime.

**K4 (experiment): add a CUDA-core matvec decode body with fine output tiles.** Hazy found that for batch-1 matvec on Hopper it is "better to simply run on the CUDA cores" ([No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)), and their 16-row blocks let every op split into at least `sm_count` instructions. Megabake's 64-row WGMMA tiles leave the 32-tile 1.7B projections on **32 of 60 SMs at 70–72% of peak** ([ROADMAP.md:64](../ROADMAP.md)). A 16- or 32-row body would put twice to four times as many tiles in flight. Measure it against the inert-code control before trusting any gain.

**K5 (hygiene): keep every trap warp-uniform.** The VM's dispatch falls through to `trap` on an unknown opcode ([TK OLD util.cuh](https://github.com/HazyResearch/ThunderKittens/blob/50ee1f0a/prototype/vm/util.cuh#L43-L58)). That is harmless only because the opcode is uniform across the warp. Megabake's C7519 root cause was a per-lane trap, fixed by `trap_if` voting across the warp ([runtime.py:143-154](../src/megabake/runtime.py)). Any new role dispatch or default arm must keep this property, and `tools/wgmma_serialization.py` should gate every change.

## IR stack: typed instruction records instead of positional columns and string surgery

### What Hazy built

On Megakernels main, an instruction is 32 int32 words. Word 0 is the opcode, and Python serializes dataclass fields in declaration order, writing lists as a length followed by the elements ([instructions.py](https://github.com/HazyResearch/Megakernels/blob/main/megakernels/instructions.py#L83-L119)). Each C++ op reads `instruction[k]` by position, and nothing checks the two sides against each other ([matvec_adds.cu](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/matvec_adds.cu#L21-L38)). Model dimensions are macros (`LLAMA_1B_HIDDEN_DIM 2048`), the op list is a compile-time template pack, and adding an op touches five places across C++ and Python ([llama.cuh](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/llama.cuh#L7-L26)). mk-v2 fixed most of this. Its instruction is a `static_assert`ed 256-byte struct holding explicit `src_tensors[16]`, `dst_tensors[8]`, `indices[16]` and separate source and destination barrier lists, with a pydantic model that "Must match `struct instruction_t`" ([mk-v2 schema.cuh](https://github.com/HazyResearch/Megakernels/blob/mk-v2/csrc/schema.cuh#L25-L44); [mk-v2 instruction.py](https://github.com/HazyResearch/Megakernels/blob/mk-v2/megakittens/schema/instruction.py#L17-L50)). A C++20 concept enforces the five role structs. Dispatch is JIT-generated per graph, with a fresh icode for each unique `(itype, src_tensors, dst_tensors)` so tensor indices become compile-time constants ([mk-v2 dispatcher.py](https://github.com/HazyResearch/Megakernels/blob/mk-v2/megakittens/dispatcher.py#L321-L347)). New itypes are discovered automatically through `IType.__subclasses__()`.

The mk-v2 docs still carry rules a type system should enforce: "Every page claimed must be released", "`init_semaphores` must return the count ... Getting this incorrect results in undefined behaviors" ([mk-v2 CLAUDE.md](https://github.com/HazyResearch/Megakernels/blob/mk-v2/.claude/CLAUDE.md)). Those same docs point to reference files (`itypes/add.cuh`) that do not exist in the tree.

### What megabake does today

Megabake's upper IR is already richer than anything Hazy built. It has about eight frozen-dataclass layers, from `ComputeGraph` with per-op `TensorProgram` loop nests ([lowering.py:16-156](../src/megabake/lowering.py)) through region matching, body selection with typed `BodyConfig` contracts ([interface.py:138-150](../src/megabake/bodies/interface.py)), tile maps, typed `RegionDependency` kinds including WAR and WAW ([schedule.py:26-65](../src/megabake/schedule.py)), and phase or event schedules, down to `KernelPlan`. The weak layers are at the bottom.

The emitted phase table is positional: column 0 is the variant, 1 the barrier ordinal, 2 the rotation (−1 means recompute), and 6 onward hold tensor slots ([codegen.py:1205-1239](../src/megabake/codegen.py)). This is the same brittle encoding Hazy's main branch had. Bodies are composed by text surgery. `_nested_body_source` parses a body's standalone `@cute.kernel` source with `ast`, keeps only `run`, and string-replaces decorators, thread-index lines and `scratch[block,` ([codegen.py:2314-2353](../src/megabake/codegen.py)). `_affine_work_iterator` string-replaces `work_iterator[tile]` ([codegen.py:2356-2365](../src/megabake/codegen.py)). The recorded consequence is that "helper functions in a body's source are dropped, so inline the code" ([cute-dsl-kernel-gotchas](/home/dev/.claude/projects/-workspace-megabake/memory/cute-dsl-kernel-gotchas.md)).

No IR layer owns cross-phase resources, so the whole launch is forced into one GEMM layout. Codegen raises "table-launched GEMMs must share one tile and shared-memory layout" ([codegen.py:1420-1423](../src/megabake/codegen.py)), swapAB is all-or-nothing ([interface.py:36-43](../src/megabake/bodies/interface.py)), and generic bodies are force-widened to the GEMM's 256 threads ([codegen.py:2104-2130](../src/megabake/codegen.py)). The `EventSchedule` IR is fully built but unused for full models ([codegen.py:556-629](../src/megabake/codegen.py)).

### The lesson

mk-v2 is Hazy converging on megabake's architecture from below: trace, tile, derive barriers, generate dispatch. Megabake's top half is ahead. It has typed dependencies and contract-based selection, where Hazy has hand-written DAG builders. What megabake should take is mk-v2's bottom half. A **typed per-instruction record shared by host and device**, with explicit tensor, index and RAW/WAR wait lists, retires the positional-column brittleness that Hazy themselves had to retire. **Resource ownership as a first-class plan layer** (pages, roles, register budgets) is what Hazy's controller did at run time and what megabake currently fakes with tags and union layouts. Megabake can compute in the compiler what Hazy computed by hand. Its schedule is static and each CTA's op sequence is known at bake time, so the `release_lid` permutation becomes a derived fact rather than a hand-written table.

Generated specialization needs a warning. mk-v2's per-`(itype, tensors)` icodes push every tensor index to compile time, which multiplies code. Megabake measured the opposite tradeoff: flattening the table indirection helped, and the 2026-10-22 cleanup gained 0.5–3.3% purely from code shape and table size ([cleanup-2026-10-22](/home/dev/.claude/projects/-workspace-megabake/memory/cleanup-2026-10-22.md)). Because ptxas allocates registers for the whole kernel, specialization has to be decided per variant by measurement, not taken as a default.

### Recommendations, in priority order

**I1 (high, cheap): replace positional phase-table columns with a typed `PhaseRecord` schema.** One Python dataclass should generate both the host packer and the device-side accessor source, with a layout hash checked at load. It should carry explicit fields for variant, wait list, signal list, rotation, units, page assignment and preload descriptors. This is mk-v2's pydantic-mirror lesson applied to megabake's existing table.

**I2 (high): add a `ResourcePlan` layer to `KernelPlan`.** It should record role layout, per-role register budgets, a shared-memory page pool (fixed-size pages, sized for one GEMM stage), and for each CTA the per-phase page acquire/release order. The release order should be derived from the static schedule, not hand-written as Hazy's `release_lid` was. Per-GEMM tile configurations follow from this: when shared memory is a page pool rather than one union layout, the "must share one tile" restriction no longer has a structural reason to exist.

**I3 (medium): retire string surgery for body composition.** CuTe DSL is Python, so bodies can be `@cute.jit` role functions in importable modules, parameterized by constexpr arguments and called from generated dispatch code, instead of `@cute.kernel` source text re-parsed with `ast`. Whether the DSL inlines imported jit functions well inside a megakernel needs a quick ptxas check (`CUTE_DSL_KEEP=ptx`), which takes about 1 s per try. Hazy's lesson is that per-op role hooks are the right unit. Megabake's own lesson is that text replacement silently drops code.

**I4 (medium): turn the profile into an oracle.** Add per-phase, per-role timing slots compiled out by a constexpr flag, as the VM did (`TIMING_RECORD_ENABLED`, with an average overhead of **0.39%, maximum 1.07%**, [TP-Llama main](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-main)). Use them with the reference implementation, numerics tolerances and the existing inert-code control to define an expected Gantt chart per model. Check regressions against that chart, not only against end-to-end time. This is the oracle that the "Retire" post says must outlive any layer you remove.

## Scheduler and sync: counters pay only when a loader can run ahead

### What Hazy built

The latency VM schedules "each SM's instruction sequence ahead of time on the Python side" and reuses it "for hundreds of forward passes" ([No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)). The default SM assignment is round-robin ([generate.py](https://github.com/HazyResearch/Megakernels/blob/main/megakernels/scripts/generate.py#L47-L48)). Most of the scheduling intelligence actually lives in **hand-coded partitioning**: one QKV instruction per SM, strided up/gate block lists, and down-proj cut at column-split boundaries ([latency/scheduler.py](https://github.com/HazyResearch/Megakernels/blob/main/megakernels/demos/latency/scheduler.py#L118-L232)).

The schedulers that try to do more are broken. `assign_dag_to_sms` sets `start_time = sm_time` and has the dependency-aware `max(ready_time, sm_time)` **commented out**, and the call to its critical-path priority is also commented out ([scheduler.py](https://github.com/HazyResearch/Megakernels/blob/main/megakernels/scheduler.py#L94-L151)). The throughput DAG has no edges at all, plus a "TODO: these dependencies are broken" ([throughput/scheduler.py](https://github.com/HazyResearch/Megakernels/blob/main/megakernels/demos/throughput/scheduler.py#L317-L322)).

Cross-SM synchronization uses global-memory counters, and on main the expected counts are literals inside op bodies: `512` for the next layer's QKV, `4` per head, `num_attention_heads` for O-proj ([matvec_adds.cu](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/matvec_adds.cu#L181-L192)). The host resets the counters with `barriers.fill_` before every token, which costs an extra kernel per step ([generators.py](https://github.com/HazyResearch/Megakernels/blob/main/megakernels/generators.py#L115-L143)). The spin-sleep constant is declared `static constexpr bool GMEM_SPIN_LOOP_SLEEP_NANOS = 20`, so every `__nanosleep` gets 1 instead of 20. This is an inference from C++ semantics, never benchmarked, and mk-v2 quietly retyped it as `int` ([config.cuh](https://github.com/HazyResearch/Megakernels/blob/main/include/config.cuh#L48); [mk-v2 schema.cuh](https://github.com/HazyResearch/Megakernels/blob/mk-v2/csrc/schema.cuh#L73)). The release fence before each signal is commented out with "possible we need sc here but I don't think so" ([matvec_adds.cu](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/matvec_adds.cu#L165-L176)). TK 2.0 later reported that "a few loose fence instructions caused over 10% loss in performance" ([TK 2.0](https://hazyresearch.stanford.edu/blog/2026-02-19-tk-2)), and ThunderKittens fixed missing memory clobbers on mbarrier waits as late as September 2026 ([commit b62aa152](https://github.com/HazyResearch/ThunderKittens/commit/b62aa152)).

The good ideas are in the granularity. Up/gate signals per 2048-wide column chunk, so down-proj waits only for its own column. Attention waits only on its own heads. **Only the last KV block of the last attention partial waits for the newly appended K/V, so the earlier cache blocks stream in while the current token's QKV op is still running** ([attention_partial.cu](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/attention_partial.cu#L357-L383); [upgate.cu](https://github.com/HazyResearch/Megakernels/blob/main/demos/low-latency-llama/upgate.cu#L117-L120)). mk-v2 derives all of this automatically. It computes a GCD unit region per edge, creates **one barrier per unique (producer node, set of producer instructions)**, keeps separate RAW and buffer-reuse (WAR) lists, and spins relaxed followed by a single `fence.acquire.gpu` ([mk-v2 scheduler.py](https://github.com/HazyResearch/Megakernels/blob/mk-v2/megakittens/scheduler.py#L186-L288); [mk-v2 utils.cuh](https://github.com/HazyResearch/Megakernels/blob/mk-v2/csrc/utils.cuh#L26-L69)). Its waits test equality against exact targets, so an over-arrival deadlocks.

On dynamic scheduling, Hazy's own data is clear. The latency kernel stayed static because "the latency of this atomic increment would be prohibitive". The global queue only pays when "individual instructions frequently take 100 microseconds or more", and "At very small batch sizes, the overhead in the global work queue actually outweighs its benefit" ([TP-Llama main](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-main)). The interpreter itself is affordable only because instructions run "at the granularity of dozens of microseconds" ([TP-Llama intro](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-intro)). Hazy's B200 breakdown attributes **250 of ~600 µs to storing activations, awaiting consistency and reloading**, against 80 µs of interpreter setup and overheads ([No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)).

### What megabake does today

Every CTA walks one global phase list. Work is partitioned statically into contiguous tile ranges per CTA, rotated so that concurrent phases start on different CTAs ([schedule.py:1504-1520](../src/megabake/schedule.py); [codegen.py:1220-1232](../src/megabake/codegen.py)). Barrier intervals are separated by a monotonic counting grid barrier: one `red.release.add` arrival and acquire polling, **about 0.7 µs at 60 CTAs** ([runtime.py:157-199](../src/megabake/runtime.py); [ARCHITECTURE.md:86](../ARCHITECTURE.md)). Ordinals are dense per call, so megabake needs no counter reset between calls ([codegen.py:1371-1379](../src/megabake/codegen.py)), which is already better than Hazy's per-token `fill_`. Small producers are folded into their consumer's interval as redundant recompute ([schedule.py:1383-1501](../src/megabake/schedule.py)). That is megabake's version of Hazy's fused "RMSNorm + QKV" instruction, which performs "identical RMS computations over a hundred times" ([TP-Llama main](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-main)).

Event counters exist (`publish_event` and `wait_for_event` with `(epoch+1)*trigger_count` targets, [runtime.py:287-324](../src/megabake/runtime.py)) but are emitted only for small parameter-launch graphs. The measured bound is the key fact. SmolLM-135M decode runs **278 phases in 151 intervals, with barrier release at ~11% of the span**. The gap report's estimate that events would save 17–30% was refuted, and events alone would gain little because "the critical path is per-phase work latency" ([ROADMAP.md:93](../ROADMAP.md); [event-runtime-milestone](/home/dev/.claude/projects/-workspace-megabake/memory/event-runtime-milestone.md)). L2 prefetch of the next weights by every CTA made decode **16–24% slower** and was removed.

### The lesson

Megabake's finding and Hazy's design agree once you see what Hazy's counters were for. Hazy did not win by replacing barriers with counters. It won because counters let a **persistent loader start the next instruction's loads while the current one drains**, and because dependencies were cut finer than whole ops (per head, per column chunk, last KV block only). Without a decoupled loader there is nothing to fill the time a counter frees up, which is exactly why megabake measured little gain from events. The order therefore matters: roles and pages first (K1, K2, I2), counters second. Weight loads need no counter at all, since weights are read-only. Only activation loads and buffer reuse do, and that is precisely mk-v2's RAW/WAR split.

### Recommendations, in priority order

**S1 (keep): static assignment, monotonic per-call ordinals, and grid barriers as the default.** Hazy's evidence backs ROADMAP's "do not build a dynamic work queue" for batch-1 decode. Megabake's epoch scheme is strictly better than host `fill_` resets.

**S2 (after K1/K2): add counters only on edges a running-ahead producer can use.** Candidates are GEMM→GEMM edges where the next GEMM's activation tile depends on a subset of producer tiles, attention partial chunks, and the KV-append edge, where Hazy's last-block-only wait is a direct template. Derive barrier ids and targets from tile-region overlap as mk-v2 does, using megabake's existing `TileAccess` and `RegionDependency` data, with separate RAW and WAR lists in `PhaseRecord`. Keep `>=` tests against monotonic epoch targets rather than mk-v2's exact equality, so an over-arrival cannot deadlock.

**S3 (cheap): write down and test the memory-model contract.** For each sync site, record the release side (drain async stores, `fence.proxy.async`, `red.release`) and the acquire side. Benchmark mk-v2's relaxed spin plus one acquire fence against megabake's `ld.acquire` polling. Type every sleep and backoff constant explicitly. ARCHITECTURE already states the rule ([ARCHITECTURE.md:110](../ARCHITECTURE.md)). Hazy's commented-out fences and their 10% fence penalty show why it has to be enforced in codegen, not left to comments.

**S4 (medium): make partitioning part of the cost model.** Hazy's real scheduler was choosing how much work goes into each instruction so that every op fills the SMs. Megabake's idle-SM problem (attention on 9/60 CTAs, projections on 32/60) belongs to the same choice. It should feed ROADMAP step 7 (`TargetFacts` plus per-GEMM configs), together with K4 and the existing split-K and decode-chunk knobs.

**S5 (if built): get list scheduling right.** If megabake ever assigns tasks by list scheduling, it must include ready times and critical-path priority, the exact parts Hazy commented out. Validate it with `simulate_event_schedule` ([schedule.py:689](../src/megabake/schedule.py)) against the measured Gantt chart before emitting it.

## Phased roadmap and what not to adopt

The roadmap orders changes by expected payoff per unit of effort and keeps the project's rule that GPU benchmarks run in batches against an inert-code control. Payoff labels are qualitative. The only measured bounds are that barrier release is ~11% of decode span, that GEMM intervals are ~3–4 µs each and dominated by fill, and Hazy's 10.2→3.4 µs gap reduction from cross-instruction pipelining.

| Phase | Change | Addresses | Payoff | Effort |
|---|---|---|---|---|
| 0 | Typed `PhaseRecord` schema (I1); constexpr-gated per-phase/role timing slots and expected-Gantt oracle (I4); written memory-model contract and typed constants (S3) | String/positional brittleness, A/B noise, fence correctness | Enables everything after; small direct perf | Low |
| 1 | Fixed role layout: dedicated producer warp, two consumer warpgroups with named barriers, per-role `setmaxregister` (K1); move weight preload to the producer warp; keep `trap_if` and serialization checks (K5) | Streaming blocked on TMA queue; whole-kernel register coupling; all-thread syncs | High: makes streaming viable and turns register budgets into contracts | High (every body on 7 warps) |
| 2 | Persistent GEMM pipeline state across phases (K2); `ResourcePlan` page pool with compiler-derived release order (I2); per-GEMM tile configs | GEMM fill/drain per phase; one-layout-per-launch | High on decode GEMM intervals | Medium–high |
| 3 | Role-function bodies with hook slots, replacing `_nested_body_source` (K3, I3) | String-surgery composition, dropped helpers | Medium (velocity, fewer codegen-shape artifacts) | Medium |
| 4 | Counters on selected edges derived from tile overlap with RAW/WAR lists (S2); partitioning in the cost model (S4); CUDA-core matvec decode body experiment (K4) | Per-phase latency, idle SMs | Medium; bounded by ~11% barrier share plus the idle-SM share | Medium |

Phase 3 can start in parallel with phase 1 if converting bodies to roles proves painful through text replacement. Phase 4 should wait until phase 2's profile shows a producer warp actually stalling on a dependency that a finer counter would remove.

The following are explicitly not worth adopting, each for a reason Hazy's own record supplies.

| Do not adopt | Why |
|---|---|
| A general on-GPU opcode interpreter with a linear dispatch chain inlined into every role | Deleted from TK main; forces every op into the union register budget (104 regs); affordable only for multi-µs instructions |
| Per-SM NoOp-padded queues keyed on `%smid` | Silently assumes one block per SM and grid = SM count; megabake's rotation already gives static per-CTA work |
| Hand-written `release_lid` tables and literal barrier counts in bodies | Couples bodies to one model shape and pipeline depth; still `static_assert`-pinned in mk-v2; megabake can derive both |
| Host-side counter reset per call | An extra kernel per token; megabake's epoch ordinals already avoid it |
| Exact-equality counter targets | Over-arrival deadlocks; keep monotonic `>=` |
| The Megakernels DAG list scheduler as written | Ready time and critical-path priority are commented out; the throughput DAG has no edges |
| A dynamic global work queue or CLC work stealing for batch-1 decode | Hazy measured the atomic as prohibitive at small instruction sizes; revisit only for long prefill instructions or Blackwell co-scheduling |
| Sixteen thin consumer warps | Hazy's 2026 kernels moved to fewer, fatter consumers (8 warps at 224 regs in mk-v2) |
| Undocumented fences and untyped config constants | The `bool` nanosleep and the commented-out release fences are latent bugs; loose fences cost Hazy >10% |
| Replacing the compiler with agent-written bespoke megakernels | Hazy's own caveat: bespoke kernels do not "stratify" verification and only work with a strong oracle. Megabake's value is the shared, derived surface; adopt the oracle, not the retirement |
| Green contexts for SM partitioning | MoK found them "unreliable at partitioning SMs exactly as intended" |

## Conclusion

The comparison changes what megabake's measurements mean. Weight streaming, L2 prefetch and event counters each failed on their own, which reads like evidence that cross-op overlap does not pay on this hardware. Hazy's design suggests a different reading: each of those features is one leg of a three-legged structure (persistent roles, paged shared memory, fine-grained counters), and none stands up alone. The next experiment worth running is therefore not another streaming variant but the role split. If a dedicated producer warp with persistent pipeline state does not hide the GEMM fill measured in megabake's own profile, that is strong evidence against the whole family of techniques, and megabake can stop spending on them.

Hazy's arc also says which parts of megabake are durable. Their hand-built layers were deleted within months, while the derived parts (automatic barriers, traced graphs, generated dispatch) are what the 2026 rewrite converged on. Megabake already owns those derivations. Its main risk is not missing a Hazy feature but spending effort on whole-kernel codegen artifacts, which is why the typed record, the resource plan and the Gantt oracle belong first even though they look like plumbing.
